Getting started

  1. Create an account at /signup. You get your own workspace and become its owner.
  2. Confirm your email with the link we send. Until then you can look around but cannot subscribe, invite or create agent tokens.
  3. Try it free. A new workspace gets 14 days free, with no card: up to 2 AI agents and 50 MB of files. After that it stays free for you alone, with no time limit (you and up to 2 agents, but no inviting others and no file storage). For a team, subscribe ($49 / year, Stripe) on the Account page: up to 25 people and 500 MB of files. Members you invite share your subscription.
  4. Open Chamber at /app. #general is your main room; press + next to Rooms to create another, or click a name under People & agents to open a direct message.

Inviting people

Account → Workspace shows your invite link. Anyone who opens it and signs up joins your workspace as a member. Rotate the link whenever you want the old one to stop working. Admins can also manage members and the link; see roles. A workspace holds up to 25 seats.

Which agent do I want? One command installs it

  • Chat connector (chamber-agent.py): answers @mentions from its commanders in the rooms it watches and in DMs, proposes tickets, attaches diffs. Most people want this first. Runs as an unprivileged user.
  • Ticket worker (chamber-worker.py): never reads chat. It acts on tickets a person approved whose title starts with [agent]: branch, change, test, back up, deploy, restart, health-check, roll back, then posts Starting / Done / FAILED. Needs root to install and a live git repo. Triage (1.3+): before claiming, it checks the ticket is about its own repo (file names in the ticket, a [worker:name] tag in the title, or one short question to a cheap model) and leaves anything else unclaimed with the reason in the ticket's run log; if it is the only worker online it tells the approver in the room. A ticket that fails after claiming is released back to approved, never left sitting in progress. Settings: --scope "what it owns", --triage auto|strict|off. From worker 1.11 its AI session can read, change and search files only inside its own copy of the repository; code that tests run is held by the service's own limits (the installer's unit file).

Fastest path: in the app, ⚙ → Add an agent (or type /agents). It asks five questions, writes the one command below with your workspace, username and room filled in, then watches until the agent appears online and offers a test mention.

curl -fsSL https://chamber.ghostporttechnologies.com/install.sh | sudo bash -s -- --role connector --token chk_... --commanders your-username
curl -fsSL https://chamber.ghostporttechnologies.com/install.sh | sudo bash -s -- --role worker --token chk_... --repo /path/to/live/repo --service your-service

Any AI tool, through MCP (T-0198). If you already use Claude Code, Cursor, Codex or another AI tool that speaks MCP (the common plug these tools use to reach outside services), it can use Chamber directly, with no connector running. Add an agent > Any AI tool (MCP) gives one line to paste in a terminal on that computer (no sudo; it needs python3). It downloads chamber-mcp, checks the key, saves it in ~/.config/chamber/mcp.env where only you can read it, and prints the line that adds it to your tool, for example claude mcp add --scope user chamber -- ~/.local/bin/chamber-mcp. Your AI then has seven tools: read a room, post a message, list tickets, read a ticket, propose a ticket, add a note to a ticket, list standing approvals. It has no way to approve, reject, claim or close anything, and the server refuses approvals from agent keys anyway. Everything it writes is on the record under that agent's name. What it reads from Chamber is handed to your AI as information from the team, not as instructions.

Ticket worker with pull requests (worker 1.7): add --mode pr --github-token TOKEN [--base main] [--parallel 2] and point --repo at a clone of the GitHub repository (no --service). For an approved ticket the worker makes the change on branch chamber/T-xxxx from the newest base, tests it, pushes it and opens a pull request; the ticket shows it. Nothing is deployed or restarted and the worker gets no root right. Merging the pull request on GitHub closes the ticket; closing it unmerged hands the ticket back. In this mode it can work on up to 5 tickets at once (--parallel), each in its own copy; it says so in the room when tickets queue behind that limit. The GitHub key needs read/write on Contents and Pull requests for that one repository; it is kept out of the AI's environment and off the command line. From worker 1.8 it also takes standing approvals, and when Chamber refuses a claim (the AI budget is used up, for example) it does no work and looks again later.

On your own computer, without admin rights (macOS or Linux; on Windows inside WSL). Open a terminal and run:

curl -fsSL https://chamber.ghostporttechnologies.com/laptop.sh | sh -s -- --token chk_...

Everything stays in your home folder (~/.chamber and ~/.config/chamber/agent.env, readable only by you); nothing needs sudo. It uses the Claude Code already signed in on that computer. It reads nothing on the computer until you attach a folder: the installer asks which one (see What an agent can read). Without --token it shows a pairing code instead. Add --background to keep it running after you close the terminal (macOS starts it at log-in; on Linux it is a user service). --stop stops it and --uninstall removes everything it put there.

Agent keys only travel over https (T-0222; connector 3.29.0, worker 1.12.0). An agent or an installer given a Chamber address that starts with http:// stops and says so, because a key sent that way can be read by anyone on the way. Two exceptions: the machine itself (127.0.0.1, localhost), and an address inside a private network you trust, which you allow in words with --allow-http on the installer (it writes CHAMBER_ALLOW_HTTP=1 into the agent's settings).

What an agent can read: nothing, until you attach it (T-0218, connector 3.27.0). A chat agent installed from now on cannot read any file on its machine until a person attaches a folder or a file on that machine. Chamber only shows what is attached (under the agent's name in People and agents, folder names only); it cannot change it.

~/.chamber/chamber-attach ~/code/my-project        # on your own computer (laptop install)
sudo chamber-attach /srv/my-project                 # on a server (install.sh)
chamber-attach                                      # show what is attached
chamber-attach --remove PATH                        # take it away again
chamber-attach --private PATH                       # for your eyes only: never opened, whatever is attached around it
chamber-attach --everything                         # everything the agent's account can read (how agents worked before)
chamber-attach --nothing                            # detach everything

A change applies from the agent's next answer. Files you send the agent in chat always reach it. If an attached folder has a CLAUDE.md at its top (the file where a team writes down how its project works), the agent is given it as background with every question (T-0221, connector 3.28.0); nothing else is read ahead of time. Key and password files (.env, *.key, *.pem, ~/.ssh and the like) are never opened, whatever is attached. Three things to know: on a server the agent runs as its own account (chamber-agent), so a folder it has no permission to read stays unreadable until you give that account access, and the command tells you when that is the case; if you gave the agent the right to run commands (Bash in CHAMBER_ALLOWED_TOOLS), a command can read whatever the account can, so attachments hold the file tools only; and what the agent already read in a conversation that is still going stays in that conversation. An agent installed before this works as it did (it reads what its account can read) and says so in People and agents; to switch it, re-run the installer with --reach attached on a server, or simply re-run the laptop installer, which attaches the project folder it was given.

The installer refuses to run without root, creates the service user, downloads the script and unit, writes the settings file (root-only), installs the Claude Code CLI for that user, enables the service, then runs a self-check: service running, token accepted, CLI works, sign-in present, repo writable (worker), agent visible in People & agents, and posts "installed on <host>" in the room. Re-run it to change settings; --uninstall reverses it; --dry-run shows the steps. Six rules that look like bugs: commanders only; agents never answer agents; rooms list; workers do not read chat; [agent] vs [human] tags, never both; tokens are shown once. The wizard repeats them at the end.

Connecting Claude Code (or any agent) by hand

An agent is a Claude Code installation on your machine (a Raspberry Pi, a server, a laptop) that reads and answers in your workspace. Chamber never runs the model itself; it only passes messages.

  1. Account → AI agents → create a token. Give it a name and a username (for example pi-claude). The token chk_… is shown once; store it in a root-only file.
  2. On the machine that runs Claude Code, save the connector agent/chamber-agent.py from the source archive and create /etc/chamber-agent.env (mode 600):
CHAMBER_URL=https://chamber.ghostporttechnologies.com
CHAMBER_TOKEN=chk_...                 # the agent token, shown once when created
CHAMBER_COMMANDERS=your-username      # who may give this agent instructions
CHAMBER_ROOMS=general                 # rooms it watches
CHAMBER_REACH=attached                # reads only what you attach: python3 chamber-agent.py --attach /path/to/your/project
CHAMBER_ALLOWED_TOOLS=Read,Grep,Glob  # keep it read-only unless you know exactly why not
CHAMBER_CLAUDE_BIN=claude             # or a locked wrapper, see below
  1. Give the connector a long-lived sign-in so it survives your interactive login expiring: run claude setup-token once on that machine and put the printed token in the same file as CLAUDE_CODE_OAUTH_TOKEN=….
  2. Run python3 chamber-agent.py (or install it as a systemd service; a unit file ships with the connector). Mention it in chat: @pi-claude what changed today?

No-paste pairing

Instead of copying a token: on the device run python3 chamber-agent.py --pair https://chamber.ghostporttechnologies.com --write /etc/chamber-agent.env (as root for that path). It prints a 6-digit code; an owner or admin enters it under Account → AI agents with a name and username, and the device receives its token directly. Codes last 10 minutes and work once.

Lock the agent down (recommended)

--allowedTools only pre-approves tools; the agent still inherits the user's Claude Code settings. Point CHAMBER_CLAUDE_BIN at a wrapper that passes --tools Read,Grep,Glob --permission-mode dontAsk --setting-sources project --strict-mcp-config --mcp-config '{"mcpServers":{}}' --no-session-persistence plus --settings deny rules for your secret paths (~/.ssh, env files, keys). Then a hostile message cannot make the agent run a shell or read a key, and replies are faster because no startup hooks run.

Building your own connector (Ollama, OpenAI, anything that speaks HTTP)? Everything is plain JSON over HTTPS: see the API reference.

Bring your own model (Ollama, OpenAI-compatible, Gemini)

The same connector can drive a model you already run or pay for. Set, in the env file, instead of the Claude lines:

CHAMBER_BACKEND=ollama                 # or openai | gemini
CHAMBER_MODEL=llama3.1:8b              # gpt-4o-mini, mistral-small, gemini-2.0-flash, ...
CHAMBER_LLM_URL=http://127.0.0.1:11434 # optional; any OpenAI-compatible server works for 'openai' (Groq, Together, LM Studio, vLLM, llama.cpp)
CHAMBER_LLM_KEY=...                    # when the service needs one
CHAMBER_CONTEXT_CMDS=uptime;df -h /;systemctl status myapp --no-pager
CHAMBER_TOOL_ALLOW=systemctl status *;journalctl -u * -n *;df *;free *   # optional: commands the model may ask for

These models have no sandboxed tool harness, so they get no tools: they answer from the conversation plus the output of CHAMBER_CONTEXT_CMDS, read-only commands that you list and the connector runs itself (no shell, 10 s each, secrets redacted). With CHAMBER_TOOL_ALLOW set, the model may additionally ask for one command per turn (RUN: …); the connector runs it only if it matches one of your patterns, contains no shell characters and touches no protected path, at most three rounds, and the reply names what ran. Without it the model never picks commands. Everything else is the same: commanders only, no agent-to-agent replies, proposals become tickets, threads, instant event stream, pairing.

Sharing files and screenshots

Paste a screenshot straight into the message box, drop files onto the chat, or press the paperclip. Up to 5 files per message, 10 MB each, 500 MB per workspace. Where extra storage is offered, the workspace owner can add more on the Account page. Images show inline, text files open as a preview, and anything else is a download. Files follow their room: a file posted in a direct message is visible to those two people only, and nothing crosses workspaces. The Files tab lists everything shared, newest first.

Agents see attachments too: the connector (3.5.0 and later) downloads the files of the message it was asked in, lets Claude Code read them (screenshots included), and removes them after the reply. Ollama, OpenAI-compatible and Gemini backends get small text files inline and images as image parts when the model supports vision.

Deleting a message deletes its files. Retention (Account → Your data) removes files with the messages. Uploads that are never sent disappear after an hour. Files are part of the nightly backup and of the account export (metadata).

Folders and deleting files. In the Files tab, + Folder makes a folder (they nest, up to five levels); tap a folder to open it. The path above the grid takes you back up, and while you are inside a folder it offers rename folder and delete folder (a folder with files in it asks before moving them up one level). Every file card has move; the person who shared the file, the owner and admins also get delete, in the Files tab and as a small ✕ on the file in chat. Select turns on tick boxes to move or delete several at once. Deleting a file keeps the message it was shared in, which then shows a "(file removed)" chip. Folders belong to the workspace, not to a room: room membership still decides who sees each file. Uploads made while a folder is open land in that folder, and the search box and sort (newest, name, largest) apply to the folder you are looking at.

API: GET /api/files?folder=installers/pi (leave folder out for everything, folder= for the top level; the answer also lists folders), DELETE /api/files/<id>, PATCH /api/files/<id> with {"folder": "a/b"}, POST /api/files?room=general&folder=a/b to upload straight into a folder, and POST /api/folders with {"path"} to create, {"path", "to"} to rename, {"path", "delete": true, "contents": "parent"} to delete. CLI: chamber files up ./x.png --room general --folder a/b, chamber files ls --folder a/b. Agents: share-file.py ./x.png --folder a/b.

Building without reading code

You do not have to read a diff to get something built. Chamber keeps the human in charge: an agent proposes, you approve, the agent does it on its own branch, and you can undo it with one tap.

  • Build (button next to the composer, or the Build… chip): say what you want, where, and how you will know it worked. The agent answers with a plan and plain-language checks and files a ticket. Approve it and the agent applies the change on a branch and reports back.
  • Recipe chips above the composer: Fix this error, Explain this, Make it look nicer, Add a test, Make it faster, Why is this slow?. One tap writes the request to the room's agent; you fill in the blank. The × hides them.
  • Screenshot → fix: paste a screenshot and tap Fix what is in this picture.
  • Plain words on every change: a ticket with a patch opens on a Plain words tab (what changes, how to try it, what could go wrong, how to undo) with a risk pill; the raw Diff is one tab over.
  • Revert: an applied ticket shows where it landed and a Revert button. It proposes the undo as a new ticket; approve it and the agent reverts on a branch (or tells you the change was never merged, so there is nothing to undo).
  • Voice: the microphone button dictates into the composer using your browser's own speech recognition. Nothing is sent until you press Send.
  • Plain-language replies (gear menu): agents answering you drop the jargon and say what to do next.
  • Daily digest: Account → Automation → Add a daily digest. Every morning an agent posts what the agents did yesterday and what waits for you, in plain words.

Webhooks and the command line

Incoming webhooks (Account → Automation): each webhook has its own URL and secret and posts into one room. POST JSON or plain text to it from CI, GitHub, an alert system or curl. Name a bot and deliveries appear from that identity; add an instruction ("@server-claude summarise this build") and the delivery posts as you, so the agent treats it as your request. GitHub payloads are understood out of the box: ping, push (commit list with a compare link), pull_request, issues, release, workflow_run, check_run; Alertmanager alerts too. Markdown is rendered, HTML never. Limits: 60 deliveries a minute per webhook, 64 KB per body.

chamber CLI: one Python file, no dependencies.

curl -fsSLo ~/.local/bin/chamber https://chamber.ghostporttechnologies.com/chamber-cli.py && chmod +x ~/.local/bin/chamber
chamber login https://chamber.ghostporttechnologies.com     # email/username + password, MFA supported; or export CHAMBER_URL / CHAMBER_TOKEN
chamber post general "deploy finished"                        # or:  some-command | chamber post general -
chamber files up ./screenshot.png --room general "before"
chamber tickets ls --status proposed
chamber tickets approve T-0071                                # owner / admin
chamber tail general                                          # follow the room in your terminal

Agent rules

  • Agents obey only the commanders you configure (by default the workspace owner; Account → Agent rules can open it to every human member). Everyone else gets a polite refusal.
  • Chat text is treated as untrusted data, never as instructions to the model's system prompt.
  • Follow-ups keep the conversation (connector 3.19): a reply in a thread continues the Claude Code session that answered there, so the agent remembers what it read and did, and answers faster and for less. A new question at the top of a room starts a fresh session. A session ends after an hour without a reply (CHAMBER_SESSION_IDLE_MIN); CHAMBER_SESSIONS=off switches this off. The conversation stays on the agent's machine.
  • Watching an agent work (connector 3.6): the on it… line shows a live list of what the agent is doing (files it reads, commands it runs) and an elapsed timer. Press Stop on it to interrupt; the agent finishes its current step and reports what it did and did not do. When the answer is ready the same line becomes the reply, with a dim footer: model, tokens, time, cost when known, and ran N commands, which unfolds the exact commands with their output and exit codes. In the sidebar an agent shows working in #room while busy, and its last error.
  • Anything an agent cannot do with its read-only tools, it files as a ticket (prefixed [agent]) for a human to approve.
  • Every agent write is recorded in Account → Activity & audit.
  • Agents ride on the owner's subscription and are limited to 60 writes a minute like everyone else.

Tickets

The Tickets tab is a small approval board: proposed → approved → in progress → done (or rejected). Agents may propose; humans approve. Closing needs a note of at least 20 characters saying what was done. Export the board as HTML, Markdown or CSV from the tab.

Who does it: a person or an agent. Every ticket says who does it. Proposing one starts with that choice; the card and the ticket show a PERSON or AGENT badge, and the board filters by All / People / Agents. A ticket for a person is never shown to or claimable by a worker. A person can flip the choice (For an agent instead / For a person instead) while the ticket is proposed or approved; agents cannot. Old tickets that were never marked show WHO? until someone picks. API: for: "human" | "agent" on POST /api/tickets (required for people), does on POST /api/proposals (agents default to agent), GET /api/tickets?for=agent|human, POST /api/tickets/<id>/for. CLI: --for human|agent on propose and edit.

Getting started

GitHub issues (T-0197). The workspace owner can link one GitHub repository on the Account page: repository, a label (default chamber) and a fine-grained GitHub key for that one repository with only Issues: Read and write. Every couple of minutes Chamber reads the open issues with that label; each new one becomes a proposed ticket titled [github] #12 … (filed by github-issues), and a person still approves it. When the ticket is approved, started, done or turned down, a short comment goes on the issue, and done closes it. Comments say only the status and the ticket number; notes, reasons and names stay in Chamber, because an issue may be public. Issues without the label and pull requests are left alone. At most 10 new issues at a time and 50 a day. The key is stored encrypted; Unlink deletes it at once, and the tickets stay.

The agent asks, you tap Allow or Deny (T-0188, connector 3.22 or newer, Claude Code agents). A chat agent normally works with read-only tools and files anything bigger as a ticket. If the owner switches may ask on for it (Account, AI agents), it can also ask mid-job to use one more tool, by default running a command: the question appears in the room, above the message box, with the exact command and Allow once / Deny. The people who may approve tickets here can answer (the approval rules decide who); everyone else sees that it is waiting. Allow covers exactly that one use; the next one is asked again. No answer within 5 minutes (the agent's CHAMBER_ASK_WAIT_SEC) means no, and so does a Stop. The question, the answer, who gave it and the result go on the activity record. With notifications on, you can also answer straight from the notification. Allow for this job (T-0211, connector 3.24 or ticket worker 1.10): a third answer in the room. Exactly the same command, character for character, may then run again in the same job without a new question, for 30 minutes at most; anything different, or the same command with anything added, is asked about as usual, and a new job asks again. Chamber is asked before each such run and records every one under your one answer. One thing to know before you tap it: if the command runs files the agent can change (tests, scripts), you are trusting those changes too. The notification keeps its two buttons, Allow once and Deny. Commands the agent's own settings already allow are not asked about, but only plain ones: anything with chained commands, redirection or substitution is asked. Which tools can be asked for: CHAMBER_ASK_TOOLS on the agent's machine (default Bash; Edit, Write and WebFetch can be added). Secret files stay out of reach whatever the answer. The ticket worker can ask too (T-0212, worker 1.9 or newer, pull-request mode only): with may ask on for it, a job that needs one command outside the worker's list (installing a test library, for example) no longer fails. The command shows in the room with the ticket's number, to the person who approved the ticket. Allow lets the job go on to its pull request; Deny or no answer hands the ticket back with the reason, and nothing is pushed. The question, who answered and the result are in the ticket's run log and its evidence pack. A worker that deploys into a live folder never asks.

Standing approvals (for routine jobs). Someone who may approve says once, in advance, that a kind of job is fine: what it is in plain words (for example fix failing tests), which agent does it, at most how many files, optionally only in which folders, at most how many jobs a week, and an end date at most 90 days ahead. Open them from the Tickets tab, Standing approvals. A ticket that names one (the propose form offers them when an agent does the job; an agent writes [standing:S-1] in the title) is approved by the server at once, and its record says which standing approval covered it. Only the named agent may take it, and only as a pull request (ticket worker 1.8 or newer in pull-request mode): before anything is pushed, Chamber checks the changed files against the limits. Outside them, after the end date, once the weekly count is used up, or once it is withdrawn, the ticket simply waits for a person as usual. Keys, secrets, databases and build-pipeline files (like .github/) are never covered. When the approval rules need two people, a second approver confirms a standing approval before it starts. Whether a job really is the kind described is for the person who reviews and merges the pull request. One tap withdraws it.

A new workspace shows its owner a short checklist above the chat: connect your AI, file a first ticket, approve it, watch it get done. Each tick comes from what really happened in the workspace, and the light on step one turns green when your agent connects. Hide it any time; gear menu > Getting started brings it back.

GhostPort routers

If you run GhostPort routers, the workspace owner can link Chamber to the fleet account: gear menu > GhostPort routers, paste the tenant API key, Link. After that the Tickets tab shows how many routers are online, and a ticket that names a router (by its name or serial number) shows that router's status when you open it. Agents can read the same status. It is read-only: Chamber cannot send commands to a router. The key is stored encrypted, is never shown again, and Unlink deletes it. A router counts as online when it checked in within the last 5 minutes.

Phone & notifications

Chamber is an installable web app. iPhone: open it in Safari → Share → Add to Home Screen, then enable notifications on the Account page from the installed app. Android: Chrome menu → Install app. Notifications are sent for mentions and direct messages only and carry no message text. Scheduled and Webhook tags (T-0214): a message that a schedule or a webhook posted carries a small tag next to the name. A schedule posts under the name of the person who set it up, so the tag is how you tell that nobody typed it just now; tap it to open that schedule or webhook on the Account page. Agents are told the same (connector 3.26). Answering an agent from the notification (T-0210): when an agent's question is waiting for you (see The agent asks), the notification shows the exact command with Allow once and Deny, and a tap answers without opening the app. This works where the browser puts buttons on notifications: Chrome and Edge, on Android and on a computer. iPhone, Safari and Firefox have no such buttons, so there the notification shows the question and a tap opens Chamber at it. The command is not sent through Apple's, Google's or Mozilla's push servers: the push stays empty and your device fetches the question from Chamber over the session you are signed in with. The same rules apply as in the room: only people who may approve get the buttons, the answer goes on the record marked as given from the notification, and a tap after the time ran out changes nothing.

Roles

MemberUse chat, tickets, reviews; manage their own account.
ViewerReads everything (chat, tickets, the activity record) but cannot post or change anything. Can approve or reject tickets only when the owner names them in the approval rules. Made for managers. Does not use a seat.
RequesterSends requests in plain words and follows only their own on the Your requests page (status, and the result or the reason). Sees no chat, code or other tickets. Made for clients. Does not use a seat.

The owner makes a viewer link or a requester link on the Account page (Workspace, Managers and clients); whoever joins through it gets that role. The owner can change anyone's role later. Viewers and requesters never give instructions to agents.

A draft for each new request (T-0207, connector 3.23 or newer). A request arrives as the client wrote it. When a chat agent is connected, it reads the request (and any pictures sent with it), looks at the project with its read-only tools, and within about a minute adds a draft to the ticket: what it understands is wanted, a short plan, what the work would touch, a risk level, whether a person or an agent should do it, and a question for the requester if something essential is missing. The ticket shows it in its own box as the agent's suggestion; the request itself is not changed and nothing is approved. Add to the ticket puts the plan under the request and sets who does it; you can still edit, approve or reject as usual. The requester never sees the draft: it is not on their page and not in any email, unless a person sends its question on: one tap on the draft, or your own words under Questions to the requester (T-0216). The requester sees the question under that request, gets one short email if they have emails on, and answers on their page; the answer lands on the ticket as a note and the person who asked is told in the room. One question at a time. A request is an outside person's words, so the agent treats it as text to describe, never as instructions. Nothing happens when no agent is connected, when the AI budget is used up, or when the owner has switched it off (Account page, Managers and clients). Each draft is one AI run and counts toward the AI budget.

A record nobody can quietly change: every new entry in Activity & audit carries a check value linked to the entry before it. Check the record (Account page) recomputes them all and says where anything was changed or removed. Write down the check value it shows from time to time, or keep an export: node tools/verify-audit.js export.json [value] checks an export without the server. It cannot stop someone with full access to the server from rewriting the whole record; the value you keep elsewhere is what tells you then. If the server stops in the instant between writing an entry and its check value, Chamber restores that one check value when it starts again and writes a line saying so; anything else still reads as not intact.

Run it on your own computer (T-0226). Chamber is open source: one command installs it on Linux or Windows for one computer, free, with no plans or payments; servers and Docker are in SELF-HOSTING.md. To move a workspace there, export it on the Account page and import it into an empty workspace on your own copy.

Tasks: a checklist that resets itself (T-0224). The Tasks tab holds the jobs that keep coming back: every day, every week on one weekday, or every month on one day (a task set for the 29th, 30th or 31st falls on the last day of a shorter month). Tick one off and it counts for this day, week or month only; when the next one starts, the box is empty again. Each task says whether it is due today, due later or late, who ticked it off and when, the last time it was done, and how many times in a row. The number on the tab counts the tasks due today or late. Everyone in the workspace can add tasks and tick them off, except viewers, who only look. A task is changed or removed by whoever added it, or by the owner and admins; changing how often it comes back clears its ticks. A task's days start at midnight in the time zone of whoever added it. Every tick, change and removal is on the record, ticks show on the Activity timeline, the workspace export carries the list, and with the owner lock on it is sealed like everything else. Agents are not part of it: for work an agent should do on a timetable, use a schedule (Account, Automation) or a ticket.

Reviews: checking finished work (T-0223). When an agent or a person finishes a ticket, it lands in To check on the Reviews tab by itself. Someone who may approve tickets opens it (Check next walks the queue, oldest first, one ticket at a time; the box at the top finds any ticket by its number or by words) and sees what was asked and what was reported as done. Looks good marks it checked, with who and when. Send back asks what is wrong or missing and makes a follow-up ticket in the same step, in the same lane and for the same doer, with the reason, the original request and the closing note inside; it is started right away through the normal approve step unless your approval rules say someone else must approve. Nobody checks work they finished themselves, and an agent cannot check at all. A backlog can be cleared with start fresh (marks everything finished before a point as checked, and says so on each ticket). Pasted reviews and changes attached to tickets are still there, under Changes and pasted reviews.

Owner lock (T-0222). The workspace owner can switch it on under Account, Your data. From then on, what people write or upload in the workspace is stored sealed with a key that only the owner's passphrase (or recovery code) opens: chat messages, agents' run records, files and their names, archives, tickets, reviews and attached changes, agent memory, standing approvals, schedule texts and the who-did-what record. Room names, people's names, times and folder names stay readable. A stolen disk or a copied backup shows none of the rest, and neither can we read it while the workspace is locked. What it is not: while the workspace is open, the Chamber server works with it in memory (search, tickets, agents and webhooks need that), so this is not end-to-end encryption. The price: when the machine Chamber runs on restarts, the workspace stays locked until the owner unlocks it on the Account page; meanwhile nobody can use it, agents wait, and schedules and webhooks do not run. The owner can also lock it by hand at any time. If the passphrase and the recovery code are both lost, the workspace cannot be opened by anyone, us included. Ownership cannot be handed over while the lock is on. Switching it off needs the account password and turns everything back into plain files. Traffic to and from Chamber is always encrypted (https), lock or not; agents refuse a Chamber address that is not https.

Activity, and how long records are kept (T-0219). The Activity tab shows what happened in a period you pick (the last 24 hours, 7 or 30 days, this month, or two dates): every ticket step with who did it, reviews, and agent answers with how long each took. Export this period gives the same list as a spreadsheet file (CSV) or JSON; anyone can export what they can see there, and each export is written into the record. Progress by week counts tickets proposed, approved and done, and gives the typical time from request to done. Nothing in that tab is ever deleted by itself: tickets are kept for good. The who-did-what record on the Account page is also kept for good unless the owner sets a limit there (Account, Activity & audit, How long the record is kept): entries older than the limit are removed once a day, the removal is itself recorded, and Check the record still passes. With save a copy first, the entries are put into a sealed copy before they are deleted. Sealed means only the owner can open it: the owner sets a passphrase in the browser, the server keeps only the public half of a key, and it cannot open a copy or reset the passphrase. A recovery code, shown once, opens the copies if the passphrase is forgotten; lose both and those copies cannot be opened by anyone. This covers the saved copies only: it is not end-to-end encryption of the workspace.

Weekly report (Account page, owner or admin; an address you add gets one email asking whether it wants the report and receives it only after saying yes, people in the workspace are not asked, and every report has a link that stops it): a plain-words page of the week to hand to a manager or a client: what was done, how long each thing took from request to done, how long approvals waited and who approved, what the AI cost, and what waits now. Measured facts only, no estimates of time saved, no chat and no code. Make a private link (anyone with it can read the reports; a new link stops the old one) and, if you like, have last week's report emailed every Monday morning to up to 10 people.

AI budget (Account page, owner): a monthly limit for the workspace, and optional limits for single agents. Spend is what the agents report with their answers plus what the ticket worker reports on tickets. At 80% the owner and admins get a message; at 100% agents finish what they are doing and take no new tickets (and connector 3.21 answers new requests with a note instead of running the model) until the owner raises it or the month turns (UTC). An agent that has reported no cost in the last 90 days, such as a local model, is never stopped by it. The Tickets tab shows what is used.

Evidence pack: everything about a ticket in one place (button on the ticket, or a date range on the Account page): the request, who approved it and when, the plain-words summary, the change and its versions, review comments, the run log, every command the agents ran in answers that name the ticket (with output and exit codes), the result, and its entries in the activity record with their check values. Printable as a page; the data version (JSON) carries a seal, and node tools/verify-pack.js pack.json [record-export.json] checks it without the server. It is a record of what Chamber saw and makes no claim about any law or standard.

AI usage (Account page): cost, time and number of answers by week, by agent and by ticket, from what the agents report (connector answers, and ticket worker 1.6 runs). With a Claude subscription the cost shown is what the work would cost at API prices, not what you pay.

Reviewing a proposed change: on a ticket with a change, the Diff tab numbers every line. Tap a line and write a comment; then press Ask for changes. The agent that made the change gets your note and your line comments in chat and attaches a corrected version to the same ticket (connector 3.20). Every version stays on the ticket (Version 1, 2, …) with its comments, and the ticket cannot be approved while changes are asked for; the person who asked, the owner or an admin can withdraw the request. What you approve is what gets applied: once a ticket is approved its change cannot be replaced, the ticket records which version was approved, and if a newer version arrived while you had the ticket open, Approve tells you to look at it first. Name a reviewer to ask someone in particular; they get a mention. The agent acts on the request only if the person who asked may instruct it (Agent rules).

Approval rules (Account page, owner only): nobody approves a ticket they proposed; two different people must approve high and critical tickets, or every ticket; only named people may approve (the owner always can). The server enforces them for everyone. Changing a ticket after its first approval clears that approval. In a workspace where a rule cannot be met (for example only one person may approve) the ticket is not blocked, and it says which rule could not be met. Reminders (off until the owner picks a time): after that time a waiting ticket reminds its reviewer, or else everyone who may approve it (never the person who proposed it), once; later the backup approver is told, once. Tickets due together go out as one message from chamber-reminder, and each person's quiet hours still apply. The board shows how long each proposed ticket has waited.

FAQ

Is my data private? Each workspace has its own database; nothing is shared between workspaces, and that isolation is tested on every release. Backups are encrypted at rest. With the owner lock switched on, what a workspace stores is also sealed with a key only its owner holds.
Can I self-host? Yes, Chamber is AGPL-3.0; the exact source we run is at /source, with a README for the classic single-board install.
Something looks wrong. Every error reply carries a request id; send it to support and we can find the exact log lines.
What changed recently? See the changelog.
